# 构建代理可用性检测

状态：规格就绪
来源：用户需求（2026-11-04 会话）；背景见 [正式环境 systemd 部署手册的“构建代理”](../../docs/runbooks/systemd-deployment-production.md#构建代理)

## 目标与范围

正式环境构建机（qfy-test2）直连 Docker Hub、Alpine、crates.io、npm 极慢或不通，已在构建机上运行本机 mihomo 构建代理（`127.0.0.1:17890`，由部署脚本显式注入 BuildKit，不影响同机其他应用）。代理依赖第三方订阅节点，没有 SLA，失效时部署会长时间卡住。

目标：管理员在 Deploy Go 面板上随时看到构建代理是否可用，失效时被明确提示，从而及时更新订阅并更换节点（更换仍按手册由人工执行）。

适用对象：Deploy Go 管理员。

范围：
- 控制面周期性、只读地探测构建代理并保存最近一次结果；管理员可手动立即重测。
- 设置页展示状态；代理失效时在管理员最常看到的页面给出醒目提示。
- 部署手册与安装器同步（配置项、检查方法、更换节点步骤中的面板核对）。

明确不做：
- 不在面板上上传订阅、选择或切换节点，不修改代理配置，不重启代理服务；这些仍按手册由人工执行。
- 不展示、记录或返回节点名称、服务器地址、密码或代理配置内容。
- 不修改 docker daemon、环境变量或其他业务应用；不接入 Agent 协议，不新增数据库表。
- 不探测业务节点（Agent 所在机器）的网络。

## 用户场景与验收

### US1：随时查看构建代理是否可用

- 优先级：P1
- Given：控制面已配置构建代理地址，且代理正常
- When：管理员打开设置页
- Then：看到“构建代理”卡片，状态为“可用”，并显示最近检测时间、最近一次成功时间和探测耗时
- 关键失败或边界场景：尚未完成首次探测时显示“检测中”而不是误报失败；未配置构建代理地址（如开发环境）时显示“未配置”，不发起任何探测；非管理员不能访问该信息。

### US2：代理失效时被明确提示

- 优先级：P1
- Given：构建代理曾经可用，之后探测连续失败
- When：管理员打开概览页或发起应用部署页
- Then：页面顶部出现警告，说明代理不可用、最近成功时间，以及指向更换节点手册的说明；设置页卡片状态为“不可用”并显示失败原因类别
- 关键失败或边界场景：单次偶发失败不应立即报警（连续失败达到阈值才判为不可用）；代理恢复后下一次探测成功即回到“可用”，提示自动消失；提示只对管理员显示，不阻止发起部署。

### US3：手动立即重测

- 优先级：P2
- Given：管理员刚在服务器上更换了代理节点
- When：在设置页点击“立即检测”
- Then：控制面立即探测一次并更新状态，页面展示新的结果
- 关键失败或边界场景：重复点击受冷却限制，不会并发产生多次探测；探测期间按钮不可重复提交；该操作必须通过 CSRF 校验。

### US4：探测方式与部署脚本一致

- 优先级：P2
- Given：部署脚本在构建前经代理访问 Docker Hub 判断代理是否可用
- When：面板与脚本分别探测同一个代理
- Then：判定标准一致（经代理访问 `https://registry-1.docker.io/v2/`，返回 401 或 200 视为可用），面板“可用”即代表部署脚本的预检也会通过

## 功能要求

- FR-001：控制面新增可选配置 `DEPLOY_GO_BUILD_PROXY_URL`，仅接受 `http://` 加回环地址（`127.0.0.1` 或 `localhost`）和端口；其他值使进程启动失败并给出明确错误，不得因此回显凭证。未配置时功能为“未配置”，不发起探测。
- FR-002：控制面后台任务周期性（默认每 5 分钟）经该代理探测 `https://registry-1.docker.io/v2/`，单次超时 15 秒；响应 401 或 200 为成功，其余为失败。探测请求不携带凭证，且只使用该代理，不读取全局代理环境变量。
- FR-003：状态仅保存在内存，不新增数据库表或 migration；进程重启后先为“检测中”并立即探测一次。
- FR-004：连续失败达到 2 次判为“不可用”；任意一次成功即恢复“可用”。状态取值为 `unconfigured`、`checking`、`ok`、`failing`。
- FR-005：新增只读接口 `GET /api/v1/build-proxy/status`，仅管理员可访问，响应带 `Cache-Control: no-store`，字段包括状态、最近检测时间、最近成功时间、最近耗时（毫秒）、连续失败次数和失败原因类别（`timeout`、`connect_failed`、`unexpected_status`、`tls_failed` 等有限枚举）。响应不得包含代理地址、节点或任何配置内容。
- FR-006：新增 `POST /api/v1/build-proxy/check`，仅管理员可访问并校验 CSRF，触发一次立即探测并返回最新状态；设置 10 秒冷却，冷却内重复调用返回当前状态而不重复探测，探测并发度为 1。
- FR-007：设置页新增“构建代理”卡片，展示状态、最近检测时间、最近成功时间、耗时和失败原因类别，提供“立即检测”按钮；状态用文字而不仅靠颜色表达。
- FR-008：状态为 `failing` 时，管理员在概览页和发起应用部署页看到警告横幅，不阻止任何部署操作；非管理员不请求该接口也不显示横幅。
- FR-009：OpenAPI 新增路径与 schema 登记进 `ApiDoc`，并通过 `make api-openapi`、`make api-client-generate` 生成产物，不手改生成文件。
- FR-010：安装器把 `DEPLOY_GO_BUILD_PROXY_URL` 写入 API 的环境文件并纳入白名单；未显式配置且构建机上不存在构建代理服务时不写入。部署手册同步配置项、面板核对与更换节点后的验证步骤。
- FR-011：探测日志只记录结果类别、耗时和脱敏后的失败原因，不记录代理地址之外的任何配置或节点信息。

## 成功标准

- SC-001：代理正常时，设置页在首次探测完成后显示“可用”，`GET /api/v1/build-proxy/status` 的耗时与最近检测时间合理。
- SC-002：停止构建代理服务后，不超过“2 次探测间隔加单次超时”，面板状态变为“不可用”；恢复服务后，一次成功探测使其恢复，横幅消失。
- SC-003：未配置时状态为“未配置”，探测请求数为 0；非管理员访问两个接口均被拒绝；POST 缺少 CSRF 被拒绝。
- SC-004：面板的判定与部署脚本预检一致：同一时刻两者结论相同。
- SC-005：本地可验收项（单元、接口、前端、契约测试和文档检查）全部通过；上线后的真实代理验证需要用户另行授权部署。

## 风险与验证要求

- 安全：该功能从控制面向配置的代理发起出站请求，必须限制代理地址为回环、目标固定为 Docker Hub、不透传用户输入，避免被用作任意请求转发（SSRF）；响应与日志不泄露代理地址、节点名、服务器地址或密码；接口按管理员权限和 CSRF 校验。
- 可靠性：探测任务异常不得影响部署 worker 等其他后台任务；进程优雅停止时探测任务随 shutdown 信号退出；单次探测有超时；并发度为 1。
- 验证：Rust 单元测试覆盖地址校验、状态机（连续失败阈值、恢复、未配置）和接口权限/CSRF/冷却；探测目标用本地假代理服务验证成功、超时、拒绝连接和非预期状态码；前端测试覆盖卡片各状态、横幅出现和消失、非管理员不显示；`make api-check`、`make admin-check`、`make deploy-production-check`、`make docs-check`、`make whitespace-check`；OpenAPI 与客户端生成后运行 `make api-client-check`。
- 不涉及 `cfg(target_os = "linux")` 代码、migration、Agent 线协议或 schema，无需 Linux 专项 Docker 验证。
- 真实代理与线上展示的验证需要新的部署授权，本规格的本地验收不隐含该授权。

## 未决事项

无。以下为规划时的默认选择，用户可在实施前调整：探测周期 5 分钟、连续失败 2 次判为不可用、手动重测冷却 10 秒、横幅只放在概览页与发起应用部署页、面板不展示节点名称。
