# API 启动恢复提速与部署构建缓存（紧急修复）

状态：规格就绪
来源：2026-11-11 部署 0.3.34 失败（健康检查 180 秒超时后自动回滚，API 约 6 至 7 分钟不可用）及用户追问“构建速度也是不对的，不应该有缓存构建吗？前端构建为什么要 31 秒？”。因事故紧急，实现先于本规格落笔，本文记录需求、范围与验证要求。证据与根因见[解决记录](../../docs/solutions/2026-11-11-api-startup-log-replay-and-build-cache.md)。

## 目标与范围

1. API 启动恢复不再随日志量二次增长，重启后能在几秒内开始服务。
2. 安装器不再把“进程正常、只是启动慢”误判为失败，同时崩溃重启仍快速失败。
3. 部署构建的缓存能跨部署保留，基础镜像输入固定，避免每次都是冷构建。

范围：`runtime-log` 与 API 的恢复路径、`install.sh` 的健康检查、`remote-build.sh` 与统一 Dockerfile、相关手册与契约测试。版本仍为 0.3.34（承接 015，尚未上线）。

明确不做：不改变中心日志的保留策略与水位线语义；不改 `read_page` 的对外行为；不改 Agent 协议与 payload；不手工修改线上状态；不处理同节点多应用并发部署。

## 用户场景与验收

### US1：重启 API 后几秒内就绪

- 优先级：P1
- Given：中心日志已累积到接近上限（512MiB，多个满段）
- When：API 重启并执行启动恢复
- Then：每个段只打开一次、每条记录只解析一次；恢复后的水位线与原语义完全一致；恢复期间内存占用有界
- 边界：恢复中途数据库写入失败时停止读取并报错；记录被截断（部分写入的尾部）时仍报错而不是当作读完；单条记录超出字节预算时仍能前进。

### US2：慢启动不被误判为失败

- Given：新版 API 启动较慢但进程正常（`active` 且没有崩溃重启）
- When：超过基础时限 180 秒
- Then：安装器继续等待到上限（默认 900 秒），不触发回滚
- 边界：崩溃重启（`NRestarts` 增加）、进程不再 active，仍在 180 秒失败；一直 active 但永不就绪则在上限失败；非法配置被拒绝。

### US3：构建缓存能跨部署保留

- Given：两次部署间隔超过两天
- When：再次部署
- Then：cargo 的 target、sccache、npm 缓存挂载仍在（BuildKit 对缓存挂载保留 30 天），不再重新编译第三方依赖
- 边界：基础镜像按摘要固定，上游重新发布浮动标签不使缓存失效；构建阶段 `COPY` 全部 `--link`，改动一个 crate 不连带重编无关的 crate。

## 功能要求

- FR-001：`runtime-log` 新增 `replay`（及 `SegmentStore::replay`）：顺序重放 `after` 之后的全部记录，按条数与字节数分批，回调返回 `false` 提前结束，批次边界与 `read_page` 一致且单条超限仍独占一批。
- FR-002：API 的 `DurableStore` 新增 `replay`，由文件线程读取并经有界通道交付批次；`recover_locked` 改用它，处理逻辑与水位线语义不变。
- FR-003：`install.sh` 的 `wait_for_url` 支持传入服务名；基础时限（`DEPLOY_HEALTH_WAIT_SECONDS`，默认 180）之后，服务仍 active 且没有崩溃重启时继续等到 `DEPLOY_HEALTH_MAX_WAIT_SECONDS`（默认 900）；API 的 healthz 与 readyz 检查传入 `deploy-go-api`；非整数配置被拒绝。
- FR-004：`remote-build.sh` 的 BuildKit 配置显式给出完整 GC 策略，缓存挂载保留 720 小时，其余规则与默认一致，并在本机用真实 BuildKit 验证策略生效。
- FR-005：统一 Dockerfile 与前端内联 Dockerfile 的基础镜像按 OCI 索引摘要固定；统一 Dockerfile 构建阶段的 `COPY` 全部使用 `--link`。
- FR-006：契约测试拒绝未固定摘要的 `FROM`、非 `--link` 的构建 `COPY`、缺少缓存挂载保留配置；`install.sh` 的慢启动、崩溃循环、进程退出、上限与非法配置场景有可执行验证。
- FR-007：手册记录构建缓存失效的原因与诊断方法、基础镜像摘要的更新方法、慢启动排障；新增解决记录。

## 成功标准

- SC-001：`runtime-log` 新增测试覆盖多段、批次边界、游标落点、提前停止、部分写入尾部，且与逐页 `read_page` 的结果逐项一致；API 现有的恢复测试全部保持通过。
- SC-002：本机基准：同一份数据下，满段（约 6 万条）顺序重放比按页重放快一个数量级以上，且随记录数线性增长。
- SC-003：`make api-check`、`make agent-check`、`make check` 通过。
- SC-004：Dockerfile 在本机用真实构建验证可用；对照实验显示 `--link` 使“只改 agent 时不重编无关 crate”成立（如实记录实验结果，不成立则撤回该项）。
- SC-005：上线后（需用户授权部署）API 重启后几秒内就绪，部署日志里记录各阶段耗时；本次部署为新 builder 的冷构建，之后一次部署验证缓存命中，如实记录。

## 风险与验证要求

- 恢复路径是一致性相关代码：以现有恢复测试和新增对照测试保证语义不变，不引入检查点等新机制。
- `COPY --link` 与基础镜像摘要固定属于构建输入变更，只影响构建阶段，产物仍由部署脚本校验；摘要固定后上游安全更新需要手动跟进，已写入手册。
- BuildKit 配置只在创建 builder 时生效，会新建 builder，首次为冷构建。
- 不涉及 migration、线协议与 Agent 行为；`runtime-log` crate 同时被 Agent 使用，仅新增函数，不改既有接口。
