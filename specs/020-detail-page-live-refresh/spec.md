# 详情页自动刷新的缺口

状态：规格就绪
来源：用户转述他项目的反馈“Deploy Go 详情页不自动刷新”（2026-11-12 会话）；排查后用户确认继续修复列出的缺口。

## 背景与证据

排查（代码与线上只读数据，2026-11-12）结论：部署详情页运行中本来就每 2 秒轮询状态和流程事件，日志是实时流（服务端每 15 秒保活、不会定期断开），接口响应没有缓存问题，所以“完全不刷新”不成立。但存在下列缺口，会让人觉得页面停住了：

1. **流程图在部署结束时停在旧状态。** `DeploymentFlowPanel` 的事件轮询写成“部署是终态就停止”，部署一变成终态立即停轮询，没有补最后一次。流程图的阶段状态以事件为准（`aggregateStatus` 里事件优先于阶段任务状态），而最后几条事件通常和终态结果几乎同时落库，常常晚于上一次事件轮询。结果是页面顶部徽标已经是“成功”，流程图的最后一个阶段还显示“执行中”，直到手动刷新或切换标签页重新挂载。
2. **切回标签页不会立即刷新。** 轮询在后台标签页暂停，全局默认又关闭了“窗口回到前台时刷新”，回来后要等下一个轮询周期。
3. **日志流断线次数按累计算，且放弃后不会自动恢复。** `streamSse` 的重连计数连上之后从不清零，一次部署期间累计断线 5 次（API 重启、网络抖动、电脑休眠恢复）就放弃，页面显示“连接已断开”，日志停住，要手动点“重新连接”。放弃后即使网络恢复、标签页回到前台也不会自动重试。
4. **节点详情页没有轮询兜底。** 节点状态、Agent 关联、终端能力只在 WebSocket 通知到来时刷新；WebSocket 断开后页面不会自己更新。节点列表页有 2 秒轮询，详情页没有。

## 目标与范围

让详情页在常见场景下自己保持最新：部署结束时流程图与终态一致；切回标签页立即刷新；日志流断线按“连续失败”计并在恢复条件出现时自动重连；节点详情页在 WebSocket 之外有轮询兜底。

范围（仅 Web 前端 `admin/`）：
1. `DeploymentFlowPanel`：部署由非终态变为终态时，再刷新一次事件；运行中回到前台立即刷新。
2. `DeploymentDetailPage`：运行中回到前台立即刷新详情。
3. `streamSse`：失败计数按连续失败计；`DeploymentLogPanel`：断开后联网或回到前台时自动重连。
4. `NodeDetailPage`：节点、Agent 关联、终端能力三个查询增加轮询兜底与回到前台刷新。
5. 客户端行为契约同步；测试。

明确不做：
- 不改后端、协议、OpenAPI 与生成物；不改全局 `QueryClient` 默认值，其它页面的刷新行为保持不变。
- 不在已终结的部署上持续轮询；不改日志流的服务端行为和续传语义（`Last-Event-ID`）。
- 不改应用详情页和运行日志页的刷新方式（运行日志页因共用 `streamSse` 自然受益于计数修正）。

## 用户场景与验收

### US1：部署结束时流程图与结果一致

- 优先级：P1
- Given：用户停在部署详情页的“流程”视图，部署正在运行
- When：部署完成，最后几条流程事件在上一次事件轮询之后才落库
- Then：流程图自动补刷一次，最后一个阶段显示“成功”，与顶部徽标一致，无需手动刷新
- 关键失败或边界场景：打开一个早已终结的部署时不重复请求；部署失败或被取消时同样补刷。

### US2：切回标签页立即看到最新状态

- 优先级：P2
- Given：运行中的部署详情页被切到后台一段时间
- When：用户切回该标签页
- Then：详情和流程事件立即刷新，不等下一个轮询周期
- 关键失败或边界场景：已终结的部署回到前台不发请求。

### US3：日志流短暂断线不会让日志永久停住

- 优先级：P1
- Given：部署运行期间日志流因 API 重启或网络抖动多次断开又恢复
- When：断线次数超过 5 次，或曾经连续失败后放弃
- Then：只要中间连接成功并收到日志，失败计数就从零开始，不会累计放弃；放弃后联网或回到前台时自动重连一次
- 关键失败或边界场景：连接建立后立即断开、或只收到 `stream-error` 的情况仍计入连续失败，超过上限后停止，不会热循环；已经结束的流不重连。

### US4：节点详情页自己保持最新

- 优先级：P2
- Given：管理员打开节点详情页，WebSocket 通知不可用
- When：节点状态或 Agent 状态变化
- Then：页面在一个轮询周期内自己更新，回到前台立即刷新
- 关键失败或边界场景：后台标签页不轮询。

## 功能要求

- FR-001：部署详情页的流程面板在部署状态由非终态变为终态时，立即再刷新一次事件（只在“变为终态”的那一次，不在首次加载终态部署时重复请求）。
- FR-002：部署详情查询与流程事件查询在窗口回到前台时立即刷新；部署已是终态时不刷新。
- FR-003：`streamSse` 的失败计数按连续失败计：一次连接收到过 `log` 事件，或保持连接不少于 10 秒，则计数清零；立即断开、只收到 `stream-error` 等仍计入，超过 `maxRetries` 停止。
- FR-004：日志面板处于“连接已断开”时，浏览器触发 `online` 或标签页变为可见，自动重连一次；保留手动“重新连接”；非断开状态不响应这些事件。
- FR-005：节点详情页的节点、Agent 关联、终端能力三个查询每 5 秒轮询一次（后台标签页暂停），窗口回到前台立即刷新。
- FR-006：不修改后端、协议、OpenAPI 和生成物，不修改全局 `QueryClient` 默认值。
- FR-007：`docs/standards/client-behavior-contract.md` 同步刷新与重连行为。

## 成功标准

- SC-001：回归用例——部署由 `running` 变为 `succeeded` 后事件接口被再次请求，流程图显示最终状态；修复前该用例失败。
- SC-002：回归用例——每次连接都收到日志后断开，连续 8 次后仍继续重连并收到 `terminal`；修复前停在第 6 次。只收到 `stream-error` 或立即断开仍在上限后停止。
- SC-003：断开后触发 `online` 或可见性变化，重连一次；未断开时不触发；卸载后监听器清理。
- SC-004：节点详情页在轮询周期到达后显示变化后的节点状态，无需刷新。
- SC-005：窗口回到前台，运行中的部署详情重新请求，终态部署不请求。
- SC-006：`make admin-check`、`make docs-check`、`make whitespace-check`、`make spec-kit-verify`、`make check` 通过；变异验证——去掉各项修复，对应用例失败。
- SC-007：上线后的线上验证需要用户当前对话的“部署正式环境”授权；本规格的本地验收不隐含该授权。

## 风险与验证要求

- 请求量：运行中的部署详情已有 2 秒轮询，新增的只是回到前台时各一次；节点详情页新增 3 个查询每 5 秒各一次，仅管理员打开该页且标签页在前台时发生，规模与节点列表页同级。
- 热循环：日志重连的“健康”判据（收到 `log` 事件或保持连接不少于 10 秒）避免“连上就断”的服务端造成无退避重连；自动重连只在断开后的联网或回到前台事件上触发一次，每轮重连仍带指数退避（约 23 秒封顶）。
- 影响面：`streamSse` 同时被运行日志页使用，其 `maxRetries: 8` 的含义从“累计”变为“连续”；这是预期的修正。
- 验证：Vitest + MSW 组件测试与单元测试；变异验证；`make admin-check`（lint、类型、全部测试、构建）。不涉及后端、Linux 专属代码、migration 或 Agent。

## 未决事项

无。以下为默认选择，用户可在实施前调整：节点详情页轮询间隔 5 秒；日志连接“保持连接即视为健康”的时长 10 秒。
