# 任务排队后 Git 凭证租约不再提前过期

状态：规格就绪
来源：用户需求（2026-11-12 会话）：排查他项目反馈时，线上只读数据发现的长期缺陷——同一节点的发布或构建任务排队超过 60 秒后，租约过期，任务一开始执行就失败；用户确认“要”修复。

## 背景与证据

线上只读核对（2026-11-12，生产控制面数据库）：

- **一次完整的失败**：qfy-cgb 的发布任务 15:03:31.969 创建，名下 Git 凭证租约 15:04:31.969 过期（状态已被清理为 `expired`）。同一生产节点上前一个发布占用了唯一名额，该任务 15:05:08.983 才被派发，0.27 秒后以 `secret_lease_lease_not_available` 失败。
- **规律**：全部历史中，创建到派发等待不少于 60 秒的任务共 19 个（构建 15、发布 4），全部以该错误失败，没有例外；等待不到 30 秒的 3059 个任务里只有 2 个因此失败。
- **频率**：自 2026-09-09 起累计 22 次，2026-11-05 以后占 11 次，与部署变频繁、排队变多同步增长。发布失败 7 次，测试节点 5 次、生产节点 2 次。
- **第二种触发**：上述 2 个等待 0 秒的发布任务总耗时 331 秒和 118 秒——Agent 在取租约之前先下载并校验制品，耗时超过 60 秒。成功任务从派发到取租约的间隔：构建最大 0.4 秒；发布平均 6.2 秒、最大 36.5 秒。

机制（代码）：

1. `create_stage_task` 在创建任务的同一事务里签发 Git 凭证租约，到期时间固定为“创建时刻 + 60 秒”（`api/src/agents/dispatcher.rs`）。
2. 同一 Agent 的部署名额被占满时，任务停在 `queued`；调度循环每个周期运行 `expire_secret_leases`，把过期的租约改成 `expired`。
3. 派发（`try_dispatch`）不触碰租约。Agent 取租约时，`resolve_secret_lease` 要求 `status='issued' AND expires_at>now`，不满足即返回 `lease_not_available`。
4. 现有的 `reissue_secret_lease` 只处理“租约响应投递失败”，不处理“从未被取用就过期”。

## 目标与范围

租约的取用窗口应当从“任务派发给 Agent”开始计时，而不是从“创建任务”开始：排队多久都不应让任务因租约过期而失败；租约“一次性、限定给该任务所属 Agent、限定时长”的安全属性保持不变。

范围：
1. 控制面：任务实际转为已派发（含重新派发）时，把该任务名下从未被取用的 Git 凭证租约重新计时。
2. 单元与集成测试，复现线上场景。
3. 协议标准、排障手册同步，新增解决记录；登记 019。

明确不做：
- 不改 Agent、线协议、数据库 schema、OpenAPI，不升版本号。
- 不改租约的取用规则：任务必须属于该 Agent、载荷摘要一致、租约与任务绑定、一次性、取用时必须在有效期内。
- 不处理 `secret_environment_leases`：当前控制面没有签发它们的代码路径（已全文检索 `api/src`，只有消费和清理），以后新增签发时应遵循同一规则。
- 不改 Git refs 查询任务（`application_sources`）的租约：它们创建后立即派发，不排队。
- 不改排队、并发和名额策略。

## 用户场景与验收

### US1：排队超过 60 秒的任务仍能正常执行

- 优先级：P1
- Given：同一节点的名额被前一个任务占用，新任务排队 90 秒，其租约已被清理为 `expired`
- When：轮到它派发，Agent 取租约
- Then：取租约成功，任务正常执行，而不是约 0.3 秒后失败
- 关键失败或边界场景：构建和发布两种任务都适用；任务被重新派发（Agent 重连、投递失败回到队列）时窗口再次重新计时。

### US2：租约仍然一次性且限定在派发之后的窗口

- 优先级：P1
- Given：任务已派发
- When：Agent 在窗口之后才取用、租约已被取用过、租约已被拒绝，或属于其他任务
- Then：窗口之后的取用仍被拒绝；已取用的租约不会被重新打开；其他任务的租约不受影响
- 关键失败或边界场景：窗口不得超过任务截止时间；任务没有被成功派发（被名额门禁拒绝、Agent 不在线）时不得改动租约。

### US3：取租约之前耗时较长的发布不再误失败

- 优先级：P2
- Given：发布任务派发后先下载大制品，2 分钟后才取租约
- When：Agent 取租约
- Then：取租约成功
- 关键失败或边界场景：超过发布窗口（10 分钟）或任务截止时间仍被拒绝。

## 功能要求

- FR-001：任务从 `queued` 转为 `delivered`（含重新派发）后、把任务消息发给 Agent 之前，把该任务名下 `granted_at` 为空、状态为 `issued` 或 `expired` 的 Git 凭证租约恢复为 `issued`，到期时间设为“派发时刻 + 窗口”，且不超过该任务的 `deadline_at`；只在到期时间会变晚、且任务当前仍是 `delivered` 时更新，绝不缩短。
- FR-002：窗口长度：`deployment_release` 任务 10 分钟，其余任务（含 `deployment_prepare`）60 秒。
- FR-003：任务没有被成功派发（并发门禁拒绝、Agent 未连接、状态已变化），或任务已经终结、已开始运行、仍在排队时，不改动任何租约。任务终结（失败、中断、被拒、出结果）时租约已被 `expire_task_secret_leases` 主动作废，不得复活。
- FR-004：已被取用（`granted_at` 非空）、状态为 `granted` 或 `rejected` 的租约，以及其他任务的租约，保持不变。
- FR-005：`deadline_at` 无法解析、或已早于等于当前时间时，不改动租约（沿用现有行为，不放宽）。
- FR-006：不改 `resolve_secret_lease` 的任何校验。
- FR-007：不改 Agent、协议、schema、OpenAPI。
- FR-008：协议标准、排障手册和解决记录同步说明租约计时从派发开始、窗口长度和历史证据的查询方法。
- FR-009：登记 019（`specs/README.md`、存储登记）。

## 成功标准

- SC-001：复现用例——租约已被清理为 `expired` 的排队任务派发后，`resolve_secret_lease` 返回私钥而不是 `lease_not_available`；修复前同一用例失败。
- SC-002：边界用例全部通过：窗口之后仍被拒绝、已取用的租约不被重新打开、其他任务的租约不变、门禁拒绝时不改动、非 `delivered` 状态（排队、运行、已终结）的任务租约不变、发布窗口 10 分钟且不超过截止时间。
- SC-003：`make api-check`、`make docs-check`、`make whitespace-check`、`make spec-kit-verify` 通过；变异验证——去掉派发时的重新计时，新用例失败。
- SC-004：上线后（需用户授权部署）按下列方式观察：`agent_tasks` 中 `error_code=secret_lease_lease_not_available` 的新增数量应为 0（等待 ≥60 秒的任务不再因此失败）；两个生产发布重叠时，排队的那个正常执行。真实重叠需要业务侧同时发版，不由本项目发起。

## 风险与验证要求

- 安全（凭证租约）：该租约授权 Agent 取得一次 Git 部署私钥。本改动只调整计时起点，不扩大授权对象：取用仍要求任务属于连接的 Agent、载荷摘要一致、租约与任务绑定、状态为 `issued`；一次取用后即变为 `granted`，之后不会被重新打开。窗口上限受任务截止时间约束，租约不会比任务活得更久。发布窗口放宽到 10 分钟，是因为发布任务先下载并校验制品再取租约（线上实测最长 36.5 秒、另有大制品超过 60 秒的失败），且任务本来就在该 Agent 上运行；构建任务保持 60 秒（实测取用不超过 0.4 秒）。
- 复活范围：只复活“从未被取用”的 `expired` 租约。`expire_secret_leases` 也会把已取用（`granted`）且到期的租约改成 `expired`，这些租约有 `granted_at`，不能被复活——用例覆盖。此外，任务终结时 `expire_task_secret_leases` 会主动作废它名下的租约（4 个调用点都在任务已终结之后），这些任务不会再被派发；SQL 里再加“任务当前仍是 `delivered`”的条件，即使派发与终结交错，也不会复活已终结任务的租约（那条租约也取不到：`resolve_secret_lease` 要求任务处于活跃状态）。
- 一致性：派发的状态更新与租约更新是两条语句。两者之间崩溃时，任务停在 `delivered` 且 30 秒后被回收重新排队，再次派发时重新计时，无需额外处理。
- 回滚：只涉及控制面二进制，没有 schema 或协议变化；回滚即部署上一版。
- 验证：新增内存 SQLite 集成测试（真实 `try_dispatch`、真实 `expire_secret_leases`、真实 `resolve_secret_lease` 与主密钥解密）；变异验证证明用例能抓到回退；`make api-check`。不涉及 Linux 专属代码、migration 或 Agent，无需 Linux 专项 Docker 验证。
- 上线后的线上验证需要用户当前对话的“部署正式环境”授权，本规格的本地验收不隐含该授权。

## 未决事项

无。以下为默认选择，用户可在实施前调整：构建窗口 60 秒、发布窗口 10 分钟（均不超过任务截止时间）。
