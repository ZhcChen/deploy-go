# 对外 API 扩展非生产能力时守住生产边界

背景：`specs/005-external-nonprod-management` 把 Git 来源、分支发现、应用启停、预览、探测等能力开放给外部 API Key，同时要求生产（`prod`）能力保持现状。复核发现的问题有明显的共性，记录下来供下次给对外 API 加接口时复用。

## 可复用结论

1. **“只读”不等于“可以对 prod 开放”。** 判断标准是“这个字段在改动前能不能经对外 API 看到”，而不是 HTTP 方法。`GET git-source` 含仓库地址和凭证名，既有 `sources.git` 摘要里没有，所以是新增暴露。给护栏测试分三类：既有只读（保持现状）、新增只读（对 prod 403）、写（对 prod 403）。
2. **守卫要看两个维度：应用环境和应用名下的目标环境。** 非生产应用可以带有正式环境目标（现有夹具即可构造）；任何会向应用目标的 Agent 下发任务的接口（部署、预览、探测、Env 同步重试）都要拒绝这种情况，否则会借非生产应用触达生产节点。
3. **互相兜底的守卫会让变异测试存活。** 删掉“应用非生产”检查后测试仍通过，是因为后面的“无生产目标”检查兜住了。必须构造只能被其中一道拦住的夹具（生产应用且没有任何目标），才能证明每道检查都有效。
4. **放宽访问检查要同时限制后果。** 为了让归档应用能被重新启用，状态接口不再要求应用启用，结果持 Key 者能推翻管理员的停用。放宽的同时要限定谁能撤销：这里用“只有归档它的同一个 Key”，依据是已有的审计记录，查不到就拒绝，不需要新增表。
5. **“授权”要覆盖会重新使用资源的动作，不只是新建。** 节点白名单约束新增和修改，漏掉了“重新启用被停用的目标”；停用不新增使用，应保持随时可用。
6. **管理面整体替换式接口要容忍已失效的引用。** 节点被归档后，选择器不再显示它但回传仍带上，服务端按“节点不存在”报错会让管理员无法保存。摘要里直接过滤失效引用，保存时整体替换自然清掉旧行。
7. **测试里的“别的应用读不到”要用同样合法的应用。** 用被其他守卫提前拦下的应用（如生产应用）做对照，断言会变成测别的东西。

## 方法

- 独立复核时只给范围和关注维度，不给结论；复核方没跑测试，所以每条发现都要实现方回到代码里验证，再用“撤销修复，看测试是否失败”确认因果。
- 起初把 `runtime-status` 对 prod 可读写进了计划和护栏，与规格 FR-013 直接矛盾，是复核才发现的。规格里“不新增任何对 prod 的读取”这类硬性约束，应该直接落成可执行的护栏测试，而不是在计划里重新解释。

## 补充：新增访问控制不能让原有调用方失效

8. **新的限制默认必须“不限制”，配置后才生效。** 节点白名单起初做成“未配置即拒绝”，等于上线即让所有现有 Key 的非生产写操作失效，违反“不影响原有应用”。需求里“安全、fail closed”的直觉与“向后兼容”冲突时，对一个已有调用方在用的接口，兼容优先，用显式配置收紧。
9. **“为了让原有测试通过而改原有测试”是行为变化的信号。** 当时给两个原有用例补授权被当成测试适配。验收新能力对既有行为的影响，最直接的办法是：原有测试文件相对基线只允许出现“新增”，不允许出现“修改”，并用变异（把新逻辑改回旧语义）确认这些原有测试真的在守护兼容。
10. **规格里的默认值也要用“不影响原有”过一遍。** 独立复核对照的是规格，规格写了默认拒绝，复核就不会质疑。硬性约束（不影响原有应用）要落成可执行的检查，而不是只存在于对话里。
