# API 启动恢复二次复杂度与构建缓存失效

2026-11-11 部署 0.3.34 失败：安装器等 API 就绪的健康检查在 180 秒后超时，判定失败并自动回滚。排查发现两个互相独立的问题，一个导致失败，一个让构建又慢又冷。

## 问题一：中心日志启动恢复是二次复杂度

**现象**：新版 API 进程启动后约 3 分钟内不监听端口；进程里 `runtime-log-files` 线程占满一个核（`gdb` 采样栈在 `read_page` → `read_record` → `serde_json` 反序列化），读盘量并不大（约 2MiB/秒）。

**根因**：`runtime_log_ingest::recover_locked` 为重建各来源的水位线，从序号 0 开始用 `durable.page(cursor, 500, …)` 反复读取。`read_page` 每次都要从游标所在段的开头逐条完整反序列化到游标，才能继续往后读。逐页读完一个 32MiB 的段（约 6 万条记录）要解析 `500 × 120 × 121 / 2 ≈ 360 万` 次，是二次复杂度。线上 360MB 日志（上限 512MiB）共 11 个满段，合计约 197 秒。**每次重启都必须做**（`needs_recovery` 在存在日志存储时恒为真）。

**证据（本机 release 基准，同一份数据）**：段内记录数翻倍，按页重放耗时约翻 4 倍；6 万条的满段，按页 2,226 ms，顺序重放 38 ms（58 倍）。

**修复**：`runtime-log` 新增 `replay`，每个段只打开一次、每条记录只解析一次，按条数和字节数分批；`DurableStore::replay` 由文件线程读取并通过有界通道把批次交给恢复侧，内存占用恒定。批次边界与 `read_page` 一致，单条记录超出字节预算时仍独占一批，保证不会静默中止。恢复语义没有变化，仍然是全量重放；现有的恢复测试全部保持通过。

**仍存在、未处理**：`read_page` 自身对“游标靠后”的查询仍要解析所在段的前缀（实时尾随和分页查询每次最多解析一个段，约几十到几百毫秒），没有启动恢复那样累积，暂不处理。

## 问题二：安装器把“慢启动”当成“失败”

180 秒的固定健康检查无法区分“进程在正常启动，只是慢”和“进程崩溃循环”。回滚后的旧版本同样要再恢复一次，整个事件 API 约 6 到 7 分钟不可用。现在基础时限之后，只要 `deploy-go-api` 仍是 active 且 `NRestarts` 没增加，就继续等到 `DEPLOY_HEALTH_MAX_WAIT_SECONDS`（默认 900）；崩溃循环和进程退出仍按 180 秒失败。

## 问题三：构建缓存为什么是冷的

**现象**：同一次部署，Rust 269 秒、前端 31 秒。日志显示 cargo 重新编译 272 个第三方 crate，`sccache` 0 命中 / 387 未命中，前端所有层都是 `DONE` 而不是 `CACHED`。

**原因**：
1. BuildKit 默认 GC 策略（`docker buildx inspect` 的 `rule#0`）对 `type==exec.cachemount` 在 48 小时未使用后回收，部署间隔 7 天，缓存挂载已经不在（只剩 7 天前的普通层）。此前文档里“默认 48 小时未使用才可回收”被当成了优点。
2. 前端基础镜像 `node:22-alpine` 是浮动标签，两次部署之间被上游重新发布，所有层失效。
3. 升版本号使所有工作区 crate 重编（`CARGO_PKG_VERSION` 参与指纹），这是固有成本。

**修复**：`remote-build.sh` 显式给出完整 GC 策略，缓存挂载保留 30 天，并在本机用真实的 BuildKit 验证了策略生效；基础镜像按摘要固定；构建阶段的 `COPY` 全部使用 `--link`。详见[生产部署手册](../runbooks/systemd-deployment-production.md#构建缓存为什么会失效)。

## 验证构建缓存类改动时踩过的坑

验证“`COPY --link` 能否避免连带重编”时，前后三次得出了互相矛盾的结论，原因都在实验本身，记录下来避免重复：

1. **BuildKit 计算 `RUN` 的缓存键不包含缓存挂载的 id**。只改挂载 id 并不能让旧版 Dockerfile 重新编译，它会命中本机更早构建留下的同内容层，得到“3 秒冷构建”的假结果。
2. **源码来自 `git archive` 时，所有文件的修改时间都是本次提交的时间**。实验必须模拟这一点（构建前把所有文件的修改时间刷成现在），用 `rsync -a` 保留旧时间会让 cargo 永远看不到文件变新，测不出问题。文件修改时间不参与 BuildKit 的缓存键（最小实验已证实），所以这样模拟是安全的。
3. **构建器的驱动和版本会改变结果**。同一个 `COPY --link` 的最小实验，在本机 OrbStack 内置构建器（docker 驱动，BuildKit 0.33.1）上，改了前面的层后后面的层仍被重新复制，修改时间变新；在与线上相同的 `docker-container` 驱动（BuildKit 0.34.2）上，层被复用，修改时间保持不变。结论以与生产相同的构建器为准。

## 经验

- 只在本机或测试数据上验证启动路径不够：启动恢复的耗时随线上数据量增长，测试里的几十条记录永远发现不了二次复杂度。凡是“启动时全量处理持久数据”的路径，都要有数据量上限与耗时的评估，并在部署日志里留下耗时。
- 固定的健康检查超时要区分“正在进展”和“明确失败”。
- 默认的缓存回收策略不等于你以为的行为：看 `docker buildx inspect` 打印的实际策略，而不是配置文件里写了什么。
- 部署日志留存（0.3.33 加入）第一次真实运行就拿到了定位所需的全部数据；没有它，这两个问题都只能靠猜。
