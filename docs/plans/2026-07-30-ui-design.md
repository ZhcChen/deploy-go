# UI 设计源实施计划

## 问题与目标

`admin/` 和 `admin-app/` 尚未进入正式实现，需要先用一套可运行的静态设计源验证信息架构、跨端业务语义、关键操作和异常状态。设计源必须让后续 Web 与 Flutter 实现能够依据页面、组件和状态契约开发，而不是依赖静态截图猜测行为。

本计划以 `docs/brainstorms/2026-07-30-lightweight-deployment-service.md` 为需求来源，以 `ui/docs/page-map.md` 为页面范围基线，交付可交互、可复核的 Web 与 App 管理端原型。

## 需求追踪

| 来源需求 | UI 设计责任 | 计划单元 |
| --- | --- | --- |
| R1-R3 | 节点列表、详情、创建 / 编辑入口、状态与关联记录 | U5 |
| R4-R7 | 应用列表、详情、部署目标、脚本入口与敏感值脱敏 | U5、U7 |
| R8 | 发起部署和高风险确认 | U3 |
| R9-R12 | 部署状态、时间线、日志、取消和排队语义 | U3、U4、U7 |
| R13 | 完整 Web 管理流程 | U2-U5 |
| R14 | App 的主要查看与部署操作 | U2-U5 |
| R15 | 跨端共享术语、状态和组件语义 | U1、U6 |
| R16 | 正常、空、加载、断连、失败与确认状态 | U7、U8 |

## 范围

### 本计划包含

- 设计 tokens、图标语义和共享组件状态。
- Web 工作台与 App 设备预览壳。
- 概览、部署、应用、节点四条 P0 页面主线。
- 部署确认、排队、运行、日志、成功、失败和取消流程。
- 确定性 mock 数据与场景切换。
- 响应式、键盘可达性、长文本和视觉回归复核。
- Web 与 Flutter 的设计交付文档。

### 本计划不包含

- 真实 API、登录、权限判断、SSH 或 Agent 通信。
- 正式 Web 框架与 Flutter Widget 实现。
- P1 设置、角色权限、审批、自动回滚和流水线编排的完整设计。
- 对真实部署脚本或真实凭证的保存与执行。

## 关键设计决定

### 1. 单一设计源，双端独立布局

Web 与 App 复用领域模型、tokens、状态和组件语义，但分别组织布局。Web 使用固定侧栏和高密度连续列表；App 使用底部一级导航和单列二级页面，避免把桌面页面缩小后直接放入手机壳（见 origin R13-R15）。

### 2. 零构建依赖的静态原型

运行时代码使用 `HTML + CSS + JavaScript`，入口为 `ui/index.html`，数据和交互分别放在 `ui/assets/mock-data.js` 与 `ui/assets/app.js`。使用 hash router，通过根目录 `Makefile` 的 `make ui` 启动 Python 预览服务器，默认端口为 `8050`，不依赖前端开发服务器。

### 3. 部署详情作为设计基准页

部署详情同时包含状态、时间、操作、日志和异常反馈，是最能验证产品信息层级的页面。先完成部署列表、确认和详情，再把稳定组件扩展到应用与节点页面。

### 4. 场景驱动，而非随机 mock

mock 数据必须具有稳定 ID 和固定时间线，通过场景选择器切换 `empty`、`healthy`、`running`、`failed`、`disconnected` 和 `dense`。页面刷新后结果保持可复现，不使用随机数据。

### 5. 状态不只依赖颜色

节点、应用、部署和日志流状态同时使用文字、图标和语义色。运行与危险状态有明确的动作边界；敏感参数统一显示脱敏值（见 origin R7、R9-R11）。

## 设计方向

- **产品气质**：安静、可靠、运维工作导向，优先支持扫描、比较和重复操作。
- **信息密度**：Web 紧凑但保持分组；App 保留必要摘要，将低频配置下沉到详情。
- **颜色策略**：中性色承担界面结构，品牌色只用于主要动作；成功、警告、失败、离线使用不同语义色，不形成单一蓝色或紫色主题。
- **表面策略**：页面区域采用无框布局；卡片仅用于独立重复项、确认面板和模态内容，不嵌套卡片。
- **日志策略**：日志区域使用稳定等宽字体、连续表面和固定工具条，不用装饰性终端外壳遮盖内容。
- **动效策略**：只为导航、状态切换、日志新增和反馈提供短过渡；尊重 `prefers-reduced-motion`。
- **控件策略**：过滤使用 segmented control 或菜单，二元配置使用开关，工具动作优先图标并提供 tooltip，命令操作使用明确文字按钮。

`ui/tests/ui-preview.spec.js` 用于正式浏览器回归；设计源运行时仍保持零依赖。测试工具与仓库级依赖的落点在首次实现该测试时确定，不为计划阶段预建包管理配置。

## 阶段与执行单元

### 阶段 A：设计基础

#### U1：建立 tokens、图标与组件规范

- **目标**：在页面实现前定义跨端共享的视觉和状态语言。
- **涉及文件**：`ui/docs/design-tokens.md`、`ui/docs/component-inventory.md`、`ui/assets/styles.css`
- **设计内容**：颜色、字号、间距、圆角、阴影、控件高度、断点、焦点、状态徽标、按钮、输入框、菜单、表格行、列表行、空状态、Toast、确认面板、日志工具条。
- **依赖**：`ui/docs/page-map.md`
- **验证场景**：
  1. 六种部署状态在浅色背景上可区分，且关闭颜色后仍能通过文字和图标识别。
  2. 最长状态文案和长应用名称不会撑破徽标、按钮或列表行。
  3. 键盘焦点在所有交互控件上清晰可见。
  4. Web 与 App 的触达尺寸分别满足鼠标密度和移动触控需要。
- **完成标准**：规范页能够单独展示核心 tokens、组件及其默认、悬停、聚焦、禁用、加载和错误状态。

#### U2：建立入口、路由与双端预览壳

- **目标**：提供稳定入口并隔离 Web 与 App 的布局上下文。
- **涉及文件**：`ui/index.html`、`ui/assets/app.js`、`ui/assets/styles.css`、`ui/assets/mock-data.js`、`ui/tests/ui-preview.spec.js`
- **设计内容**：`#/entry`、`#/spec`、`#/web/*`、`#/app/*`；Web 侧栏与页头；App 手机画布、状态区、底部导航和安全区；场景切换器。
- **依赖**：U1
- **测试场景**：
  1. 直接访问每个根路由都能呈现正确壳层，不出现空白页面。
  2. Web 导航激活态与当前路由一致，刷新后保持当前页面。
  3. App 二级页返回后回到真实来源，深链访问时有稳定兜底页。
  4. `1440x900`、`1024x768`、`390x844` 和 `360x800` 视口无重叠或横向溢出。
- **完成标准**：入口、规范页、Web 概览和 App 概览可切换，路由和壳层行为稳定。

### 阶段 B：部署主流程

#### U3：设计部署列表与发起确认

- **目标**：让用户能够定位部署记录，并清楚确认一次高影响操作。
- **涉及文件**：`ui/assets/app.js`、`ui/assets/mock-data.js`、`ui/assets/styles.css`、`ui/tests/ui-preview.spec.js`
- **设计内容**：Web 连续表格 / 列表、App 状态分段列表、状态与应用筛选、搜索、部署表单、目标选择、脚本与参数摘要、二次确认。
- **依赖**：U2
- **测试场景**：
  1. 空列表提供创建应用或发起部署的正确下一步。
  2. 密集历史下可按状态、应用和节点找到目标记录。
  3. 没有可用节点时不可确认部署，并明确说明阻断原因。
  4. 确认面板完整显示应用、环境、节点、脚本和脱敏参数。
  5. 返回修改后保留已选内容；确认后生成排队记录并进入详情。
- **完成标准**：Web 与 App 都能从列表或应用详情完成同语义的部署确认流程。

#### U4：设计部署详情、实时日志与结果

- **目标**：清楚呈现部署当前状态、过程输出、操作边界和最终结果。
- **涉及文件**：`ui/assets/app.js`、`ui/assets/mock-data.js`、`ui/assets/styles.css`、`ui/tests/ui-preview.spec.js`
- **设计内容**：部署摘要、状态时间线、队列位置、实时日志、跟随 / 暂停、复制、跳到末尾、断连恢复提示、取消确认、成功和失败结果。
- **依赖**：U3
- **测试场景**：
  1. 排队、运行、成功、失败、取消中和已取消都呈现正确动作。
  2. 新日志到达时，跟随模式滚动到底部；暂停后阅读位置不被抢走。
  3. 日志断开时保留已有输出并显示连接状态，不误报部署失败。
  4. 失败状态聚焦最后有效输出，同时保留完整日志入口。
  5. 超长单行、敏感值、ANSI 风格文本和空日志都不会破坏布局或泄露原值。
  6. 取消操作必须二次确认，完成后不能继续显示可用的取消按钮。
- **完成标准**：同一部署记录可以在 mock 场景中完整演示排队到结果的状态变化。

### 阶段 C：资源管理

#### U5：设计应用与节点页面

- **目标**：补齐部署前置资源的查找、查看和配置入口。
- **涉及文件**：`ui/assets/app.js`、`ui/assets/mock-data.js`、`ui/assets/styles.css`、`ui/tests/ui-preview.spec.js`
- **设计内容**：应用列表 / 详情、节点列表 / 详情、部署目标、脚本入口、连接状态、最近检查、承载关系和关联部署。
- **依赖**：U4 中稳定的状态、列表和详情组件
- **测试场景**：
  1. 在线、离线、检查中和停用节点均有明确状态与允许操作。
  2. 应用详情能够辨认不同环境和部署目标，并从目标发起部署。
  3. 节点详情能够定位受其离线影响的应用和失败记录。
  4. 已归档应用和已停用节点不会误显示可部署主操作。
  5. 地址、脚本路径、名称和最近活动超长时仍可阅读或安全截断。
- **完成标准**：用户能从节点或应用进入相关部署，并能判断资源是否具备部署条件。

### 阶段 D：跨端收敛与交付

#### U6：统一跨端组件与交互契约

- **目标**：消除 Web 与 App 在术语、状态、反馈和危险操作上的漂移。
- **涉及文件**：`ui/docs/component-inventory.md`、`ui/docs/web-handoff.md`、`ui/docs/flutter-handoff.md`
- **依赖**：U3-U5
- **验证场景**：
  1. 同一状态在两端使用相同名称、图标语义和结果文案。
  2. 两端都能找到主要操作，但布局符合各自使用场景。
  3. 每个可交互原型组件都能映射到 Web 组件和 Flutter Widget 责任。
- **完成标准**：交付文档列出组件结构、状态、交互、响应式差异和数据需求。

#### U7：补齐异常、边界与无障碍状态

- **目标**：让设计源覆盖真实管理工具中的关键非理想状态。
- **涉及文件**：`ui/assets/mock-data.js`、`ui/assets/app.js`、`ui/assets/styles.css`、`ui/tests/ui-preview.spec.js`
- **依赖**：U3-U6
- **测试场景**：
  1. 空仓库、只有节点、正常运行、失败、断连和密集历史可独立复现。
  2. 加载、无结果、局部错误和全页错误不会共用含糊反馈。
  3. 仅键盘可以完成 Web 筛选、打开详情、部署确认和日志操作。
  4. `prefers-reduced-motion` 下不依赖动画传达状态。
  5. 200% 浏览器缩放和系统大字体下，核心任务仍可完成。
- **完成标准**：页面地图中的 mock 场景都有稳定入口，关键流程满足基础可达性要求。

#### U8：视觉复核与设计交付

- **目标**：在正式客户端开发前完成跨视口验收并冻结首版基线。
- **涉及文件**：`ui/README.md`、`ui/docs/`、`ui/tests/ui-preview.spec.js`、`docs/reviews/`
- **依赖**：U1-U7
- **验证场景**：
  1. 按 `ui/docs/page-map.md` 的首轮评审路径完成全流程。
  2. 检查所有 P0 路由、浏览器控制台、键盘焦点和路由刷新。
  3. 对桌面、平板、iOS 尺寸和 Android 尺寸生成截图并检查重叠、裁切、空白和布局漂移。
  4. 对比 Web 与 App 的术语、状态和 mock 数据，确认没有契约漂移。
- **完成标准**：复核结论写入 `docs/reviews/`；阻断问题关闭后，设计源可作为 `admin/` 与 `admin-app/` 的实现基线。

## 建议执行顺序

1. U1 设计基础。
2. U2 双端壳层。
3. U3 部署列表与确认。
4. U4 部署详情与日志。
5. 先执行一次核心流程 Review。
6. U5 应用与节点。
7. U6-U7 跨端和边界收敛。
8. U8 最终复核与交付。

U1-U4 是第一里程碑，完成后必须先评审部署主流程，避免在错误的信息架构上继续扩展资源管理页面。

## 验证策略

- **静态检查**：HTML 结构、资源引用、路由表、重复 ID 和文档链接。
- **交互回归**：`ui/tests/ui-preview.spec.js` 覆盖 P0 路由、部署主流程、状态切换和键盘路径。
- **视觉检查**：使用同一浏览器工具链对固定桌面与手机视口截图，人工检查并保留关键证据。
- **运行检查**：使用 `make ui` 启动，通过 `http://127.0.0.1:8050/#/entry` 访问；控制台无错误，所有资源返回成功。
- **内容检查**：敏感参数只出现脱敏值，状态和危险操作文案与需求文档一致。

## 风险与处理

- **执行协议未确定**：UI 只表达连接、排队、运行和日志状态，不呈现 SSH 或 Agent 专属配置。
- **权限模型未确定**：首版固定管理员视角，不设计不可验证的角色矩阵。
- **并发策略未确定**：原型暂按排队展示，并在交付文档标注该状态受 API 决策影响。
- **纯 JavaScript 规模膨胀**：按路由、render helper、状态动作和 mock store 分区组织单文件；只有复杂度实际出现后再决定是否拆文件，不引入隐藏构建层。
- **双端重复设计**：先冻结共享语义与组件状态，再分别布局；不以像素完全一致作为目标。

## 完成定义

- `#/entry`、`#/spec`、所有 P0 Web 路由和 P0 App 路由可访问。
- 部署确认、排队、运行、日志、成功、失败和取消可完整演示。
- 节点和应用页面能够解释部署条件与关联记录。
- 六类 mock 场景稳定可复现，敏感值已脱敏。
- 固定桌面和手机视口无明显重叠、裁切或横向溢出。
- tokens、组件清单、Web handoff、Flutter handoff 与实际原型一致。
- 聚焦浏览器回归和人工评审通过，并在 `docs/reviews/` 保留结论。
