# Web 与 Admin App UI 完整化计划

## 初始问题

计划启动时，`ui/` 已能演示部署、应用、节点和移动端账号管理的 P0 主线，但仍属于核心流程原型，不是完整产品设计。初始问题包括：

- Web 缺少应用、部署目标和节点的新增 / 编辑闭环，设置页仍是占位页。
- `/web/apps/new`、`/web/nodes/new` 等未实现路由会被详情页通配规则接住，造成“页面可访问但语义错误”。
- App 的查看与部署主线基本成立，但登录退出、普通用户视角、失败重试、日志控制和真实状态变化不完整。
- 页面地图、组件清单、路由实现和测试清单存在漂移，部分文档声明的筛选或状态尚未实现。
- Mock 场景缺少稳定的加载、无结果、权限不足、会话失效和局部错误表现。

## 目标

- Web 形成“接入节点 -> 创建应用 -> 配置部署目标与脚本 -> 发起部署 -> 查看结果”的完整首版管理闭环。
- Admin App 形成“登录 -> 查看状态 -> 发起 / 跟踪 / 重试部署 -> 管理个人账号”的移动高频闭环。
- 唯一管理员与普通用户两类身份在导航、页面、操作和错误反馈上有可验证差异。
- 页面地图、组件清单、Mock 数据、路由和测试保持一一对应，不再用占位页或 fallback 冒充已完成页面。
- 完成后 `ui/` 可以作为 `admin/` 与 `admin-app/` 正式实现的首版设计基线。

## 范围

### 包含

- `ui/` 静态设计源中的 Web 和 Admin App 页面、交互、状态及 Mock 数据。
- Web 的应用、部署目标、节点、脚本配置、用户管理、设置和审计视图。
- App 的身份视角、部署操作、日志工具、账号自助和异常状态。
- 页面地图、组件清单、Web / Flutter handoff、浏览器回归规格和复核记录。
- 与 `docs/standards/deploy-script-contract.md` 对应的脚本契约配置与校验反馈。

### 非目标

- 不初始化正式 `api/`、`admin/` 或 `admin-app/` 工程。
- 不连接真实 API，不保存或执行真实 SSH 凭证、环境变量和部署脚本。
- 不设计自定义角色、多个管理员、审批流、可视化流水线或自动回滚。
- App 不编辑脚本、SSH 私钥、完整环境变量、Compose 或复杂部署目标配置。
- 不在 UI 计划中决定 Rust API 的 SSH / Agent 最终执行架构。

## 固定产品约束

- 系统只有一个管理员，其余账号均为普通用户。
- 系统管理功能只向管理员展示；普通用户不显示禁用入口或空壳页面。
- 用户由管理员直接创建并分配初始凭证，不发送邀请，不提供自行注册。
- Web 负责完整配置和长日志工作；App 负责查看、确认、跟踪和少量高频操作。
- 部署能力来自应用自有脚本，平台只管理脚本入口、受控参数、执行状态和输出。
- 结构色使用 GitHub 风格黑、白、冷灰；黄、绿、红、灰仅承担领域状态语义。
- App 不设计 hover，使用 pressed、selected、disabled 和 focus 状态。

## 阶段拆分

### 阶段 A：基线校正与范围冻结

- 目标：先让文档、路由和当前实现真实一致，消除假完成页面。
- 边界：不新增大页面，只修正契约、fallback 和测试清单。
- 验收重点：每个声明路由都有对应页面；未实现路由显示明确的未找到状态。

### 阶段 B：Web 完整管理闭环

- 目标：补齐首版完整配置能力，让管理员不依赖服务器命令完成部署前准备。
- 边界：复杂配置仅在 Web；敏感数据只展示脱敏 Mock。
- 验收重点：节点、应用、目标和脚本配置能够从创建走到可部署状态。

### 阶段 C：Admin App 高频闭环

- 目标：补齐移动端身份、部署操作、日志和异常体验。
- 边界：不把 Web 配置表单缩放复制到 App。
- 验收重点：管理员与普通用户均能完成各自允许的移动任务。

### 阶段 D：状态、可达性与交付冻结

- 目标：覆盖非理想状态，完成跨端契约和视觉回归。
- 边界：不扩张产品功能，只关闭遗漏、漂移和回归。
- 验收重点：所有路由、场景、权限和关键交互可稳定复现。

## 执行单元

### U1：校正页面地图、组件清单和路由

- 所属阶段：A
- 目标：建立唯一、可信的 UI 范围清单。
- 涉及文件：`ui/docs/page-map.md`、`ui/docs/component-inventory.md`、`ui/assets/app.js`、`ui/tests/ui-preview.spec.js`
- 实施内容：
  - 标记每个路由为已完成、待实现或非目标。
  - 修正 App 底部导航数量、筛选能力和账号模型等过期说明。
  - 将 Web / App 通配详情路由限制为合法资源 ID。
  - 为未知路由增加明确的 404 / 返回入口，不再 fallback 到入口页或首条 Mock 数据。
- 验证方式：遍历页面地图路由；未知资源 ID 和未声明路径均显示正确错误状态。
- 完成标准：文档、路由表和测试清单一一对应。

### U2：补齐 Web 节点接入与维护

- 所属阶段：B
- 目标：完成节点从新增到可承载部署的配置流程。
- 涉及页面：
  - `#/web/nodes/new`
  - `#/web/nodes/:id/edit`
  - `#/web/nodes/:id`
- 设计内容：节点名称、地址、区域、连接方式摘要、凭证引用、工作目录、连接测试、能力检查、启用 / 停用和受影响应用。
- 关键状态：未检查、检查中、在线、检查失败、离线、已停用、凭证无效。
- 验证方式：创建节点 -> 连接检查 -> 能力检查 -> 保存 -> 在应用目标中可选；失败时保留输入并给出具体阶段。
- 完成标准：节点接入流程可完整演示，敏感值不回显。

### U3：补齐 Web 应用、部署目标与脚本配置

- 所属阶段：B
- 目标：完成应用从创建到具备可部署目标的配置流程。
- 涉及页面：
  - `#/web/apps/new`
  - `#/web/apps/:id/edit`
  - `#/web/apps/:id`
  - `#/web/apps/:id/targets/new`
  - `#/web/apps/:id/targets/:targetId/edit`
- 设计内容：应用基础信息、环境、节点、脚本固定路径、受控参数、敏感变量引用、超时、健康检查、部署互斥和归档。
- 脚本契约：展示 Schema 版本、校验结果、缺失事件、退出码不一致和敏感输出风险。
- 验证方式：创建应用 -> 新增目标 -> 校验脚本配置 -> 保存 -> 从详情发起部署。
- 完成标准：至少一个合法目标和一个契约失败目标可稳定复现。

### U4：完善 Web 部署工作区

- 所属阶段：B
- 目标：补齐列表筛选、目标选择、失败处理和日志工具。
- 涉及页面：`#/web/deployments`、`#/web/deployments/new`、`#/web/deployments/:id`
- 设计内容：按状态 / 应用 / 节点 / 环境筛选，版本与目标选择，排队位置，取消，失败重试，日志跟随 / 暂停 / 复制 / 下载，断线恢复和结构化步骤详情。
- 验证方式：从失败记录重试并保留原任务关联；日志暂停后不自动抢夺阅读位置；断线后已有日志不丢失。
- 完成标准：排队、运行、成功、失败、取消和重试形成完整闭环。

### U5：补齐 Web 系统管理

- 所属阶段：B
- 目标：为唯一管理员提供用户、会话、设置和审计入口。
- 涉及页面：
  - `#/web/settings`
  - `#/web/settings/users`
  - `#/web/settings/users/new`
  - `#/web/settings/users/:id`
  - `#/web/settings/audit`
- 设计内容：管理员身份保护、普通用户创建与启停、初始凭证分配、当前会话、部署并发默认值、日志保留摘要和审计记录。
- 验证方式：管理员可创建 / 停用普通用户但不能停用自己；普通用户不显示设置导航。
- 完成标准：系统设置不再是占位页，管理动作有明确结果和审计反馈。

### U6：补齐登录、会话与双身份视角

- 所属阶段：C
- 目标：让 Web 与 App 都能演示管理员和普通用户的入口及权限差异。
- 涉及页面：`#/web/login`、`#/app/login`、Web 用户菜单、`#/app/mine`
- 设计内容：登录、登录失败、会话失效、退出确认、管理员视角、普通用户视角和无权限反馈。
- 验证方式：切换身份后导航和操作同步变化；普通用户无法通过深链进入系统管理页；退出后回到登录页。
- 完成标准：权限不只依赖隐藏按钮，路由层也有明确拒绝状态。

### U7：完善 Admin App 部署与日志体验

- 所属阶段：C

- 涉及页面：`#/app/deployments`、`#/app/deployments/new`、`#/app/deployments/:id`

- 验证方式：触摸流程无 hover；返回修改保留选择；普通用户只能对允许资源发起部署；失败重试生成关联记录。
- 完成标准：App 可完成一次部署从选择到结果的完整移动流程。

### U8：完善 Admin App 资源和账号状态

- 设计内容：应用 / 节点搜索，节点重新检查的状态变化，受影响资源，用户创建 / 启停结果，个人资料保存，通知开关持久化和退出确认。
- 验证方式：管理员与普通用户分别遍历五个主 Tab；页面刷新后 Mock 状态保持一致。
- 完成标准：所有可见按钮都有实际页面、状态变化或明确确认，不再只显示占位 Toast。

### U9：补齐异常与边界场景

## 建议执行顺序

1. U1 修正基线，先关闭路由和文档假完成问题。
2. U2-U3 完成节点与应用配置，这是部署闭环的前置条件。
3. U4 完善 Web 部署工作区，随后进行一次 Web 专项 Review。
4. U5-U6 完成系统管理和双身份视角。
5. U7-U8 完成 App 高频闭环，随后进行一次 App 专项 Review。
6. U9-U10 补齐异常并冻结设计基线。

## 验证方式

- 静态检查：
  - `node --check ui/assets/app.js`
  - `node --check ui/assets/mock-data.js`
  - `node --check ui/tests/ui-preview.spec.js`
  - `python3 -m py_compile ui/serve.py`
  - `git diff --check`
- 浏览器检查：使用单一 `agent-browser` 隔离会话，按页面地图逐路由验证并在结束后关闭会话。
- 服务检查：`make ui` 后直接访问 `http://127.0.0.1:8050/#/entry`；HTML、CSS 和 JavaScript 返回 `Cache-Control: no-store`。
- 权限检查：管理员和普通用户分别遍历导航、深链和危险操作。
- 视觉检查：固定视口检查卡片间距、长文本、状态徽标、底部导航、安全区和日志阅读区域。

- SSH / Agent 架构未确定：节点表单先表达“连接配置”和“凭证引用”，不承诺具体协议字段；API 决策后再冻结字段级契约。
- 初始凭证交付方式未确定：UI 只表达管理员设置和一次性提示，不在 Mock 状态中长期保存明文。
